# مذكرة تصميم: شريحة ب.2 — تطبيق الشريك «وصلة أعمال» (رحلة قراءة واحدة)

**التاريخ:** 2026-10-24 · **الحالة:** تجربة العقد نُفّذت ونجحت — المسار مُثبت والحدود التعاقدية مسجّلة (التفعيل الإنتاجي لا يزال معلّقًا على معالجة عائق القائمة §3.3)
**المرجع:** المراجعة الشاملة (ب.2) · ADR-077 (D1/D2/D4) · ADR-069 · XR-8.11 · M0-55

---

## 1. الخلاصة التنفيذية

**تجربةُ العقدِ نُفّذت ونجحت** (الأدلة: `partner-contract-experiment.e2e.test.ts` في `app-edge-e2e` · `partner-contract-experiment.integration.test.ts` في `marketplace` · اختبار الحد المسجّل في `authz-policy/policy.test.ts`). المسار مُثبت قطعةً قطعةً على الرابطِ المشتركِ (المعرّفُ العامُ نفسُهُ):

- **جانبُ الهويةِ (3/3):** إصدارُ جلسةٍ حقيقيةٍ لشخصٍ عبرَ تطبيقِ الهويةِ الحقيقيِّ على منفذٍ حقيقيٍّ بمنافذِ الإنتاجِ (`buildCustomerBotSessionPorts`) · الاستبدالُ بجمهورِ `marketplace` مسموحٌ لفاعلِ `customer` والتأكيدُ **موقَّعٌ فعلاً** (تحققٌ حقيقيّ: `sub`=الشخص · `act`=customer · `aud`∋marketplace · `via`=customer-bot) · المجهولةُ تُرفضُ · المسحوبةُ تُرفضُ بعدَ السحبِ.
- **جانبُ السوقِ (5/5):** `GET /stores/:slug/staff` بإنفاذِ العضويةِ عندَ الحدِّ — المالكُ 200 · العضوُ النشطُ 200 (القراءةُ بلا فحصِ رتبةٍ — مُقيسٌ من `listStaff` نفسِهِ) · المختومةُ 404 `STORE_NOT_FOUND` · غيرُ العضوِ 404 · بلا `obo` رفضٌ.
- **حدٌّ تعاقديٌّ مسجّلٌ:** `customer-bot` لا يملكُ جمهورَ `marketplace` أصلًا (`AUDIENCE_NOT_GRANTED` — اختبارٌ مسجّلٌ يسقطُ يومَ تُمنحُ الصلاحيةُ فيُحدَّثُ لا يُحذفُ).

**والعائق البنيوي في القائمة (§3.3) قائم:** فتحُ مدخلِ إدارةِ المتجرِ إنتاجيًا يتطلّبُ معالجةً تقنيةً (بوابة E-20 أو تصنيفٌ صريحٌ) — هذا هو موضعُ القرارِ المعماريِّ المتبقّي، لا التوافق.

## 2. أساس الاختيار المقيس (تحقيق 2026-10-24)

### 2.1 هوية wasla-core (المالك المستقبلي للهوية — ADR-077 D4)

- النموذج: **principal + membership + roles** (org_admin…) — لا `actor_type` enum أصلًا؛ جدول `session`: principal_id/token_hash/channel_type/expires_at/revoked_at.
- دورة الجلسة عبر HTTP في identity-access: `POST /v1/sessions` (إصدار — مغلق بالترخيص B-39) · `GET /v1/sessions/current` (استبطان + روابط القنوات — نصيب الطرف المعتمد من XR-6.1) · `POST /v1/sessions/revoke` (سحب — متصل بعد تدعيم B-40). **لا مسار استبدال** — مفهوم الاستبدال (جلسة ← تأكيد موجّه) نمط هوية MARKET لا CORE.
- مفهوم الشريك موجود كقناة `partner_api` («جلسة متصفح واعتماد API طريقا دخول») — لكنه نوع قناة لا دور أعمال ولا منحة.
- لا منح لـpartner-bot في wasla-core (نموذج صلاحيات مختلف).

### 2.2 مسار الشريك الحالي في wasla

- `bots/partner-bot` قائم بمنح identity (resolve + assertion:issue) فقط؛ `ASSERTION_ACTOR_BY_CALLER` يمنحه `store_staff`.
- مسارات `assertedStaff` في marketplace (beneficiary: "asserted" · ADR-060 P2) — **الوضع الافتراضي off** («لا شيء يُتحقق منه وrequest.endUser يبقى غير معرف»).
- جسر الويب `/edge/session/web` (XR-6.1) يحوّل جلسة core (برابط تيليجرام موثق) إلى جلسة سوق بفاعل السطح.

### 2.3 القرار المُقاس في marketplace (إنفاذ العضوية — معايير إثبات لا نتائج مقيسة)

- `GET /stores/:storeSlug/staff` — `tenantScoped(staffRead)` = فئة **N** (مقيس الحارس: tenantScoped ⇒ N).
- سلسلة الإنفاذ المطلوب إثباتها بالتجربة (لا نقلاً عن تعريفات الدوال): `tenantActor(request)` (obo المُنتفع) ← `listStaff(storeSlug, actorPublicId)` ← العضوية والرتبة داخل التنفيذ — **تنفيذ `listStaff` نفسه لم يُتبع بعد**، وشرط المدير الظاهر في تعليق إدارة الطاقم خاص بالتعديل (POST) ولا يُنقل إلى القراءة (GET) إلا بقياسٍ لمصدره.
- **المنح الحالية لـcustomer-bot: identity + geography + negotiations — لا جمهور marketplace** (منحة إنتاج جديدة ضرورية إن أثبتت التجربة المسار).

## 3. التصميم المقترح (الشريحة الأولى)

### 3.1 سلسلة الثقة

```
partner-mini-app (تيليجرام · طبقة المضيف الموجودة)
  → POST /edge/session (initData بسر customer-bot) → جلسة سوق actor=customer
  → الوكيل: مدخل قائمة سماح (مسار إدارة المتجر) → exchange → تأكيد المستخدم
  → نداء marketplace موقّع بـ obo (المعرّف العام للشخص) + تأكيد المستخدم
  → tenantScoped: beneficiary مطلوب + العضوية (listStaff) عند الخدمة
  → الخروج: POST /edge/session/logout (السحب) — إعادة الاستخدام تُرفض بعدها
```

**لا تعديل هوية إطلاقًا** (services/identity مجمّدة · ADR-077 D4): مبدأ D1 «حساب واحد، أدوار ملفات» — الشريك شخص بحساب واحد، وملكية المتجر **عضوية تُفحص عند الخدمة** لا فاعل جلسة منفصل. عوائق ب.2 الثلاثة المقيسة سابقًا (EdgeActorType · SESSION_ACTOR_BY_CALLER · CHECK المخطط) لا تعترض هذا المسار أصلًا — **وهذا نفسه من معايير تجربة العقد لا نتيجة مقيسة**.

### 3.2 العملية المختارة والمنحة

- **العملية:** `GET /stores/:storeSlug/staff` — مسار قائم بإنفاذ عضوية قائم (§2.3 — معايير الإثبات). قراءة فقط للشريحة الأولى.
- **المنحة المطلوبة إن أثبتت التجربة الحاجة:** سطر إنتاج في مصفوفة M1-05: `customer-bot → marketplace` بصلاحية `marketplace:staff:read` (أو ما يطابق ثوابت الحارس) — قرار تقني ضمن التفويض يُتخذ عبر مسار حوكمة المصفوفة، لا يُوسَّع بعده إلا بقرار.

### 3.3 حدود التفعيل (عائق بنيوي مقيس — يُعالج ضمن سلطة القرار لا «انتظار مالك» لكل تغيير)

| البند | المقاس | الحكم |
| --- | --- | --- |
| فئة مدخل الطاقم | `tenantScoped` ⇒ **N** (EA-CLASS-CODE) | قابل للإدراج **مغلقًا** (blocked_until) |
| فتح N إنتاجيًا | EA-OPEN-CLASS يُسقط | **ممنوع** — إلا عبر فئة P على N المقيس |
| فتح P | يتطلب شقّي E-20: تقييد المعاملات + «المنشور فقط» | **لا ينطبق دلاليًا** على قراءة إدارة الطاقم (ليست موردًا منشورًا للتصفح العام) |
| مسارات assertedStaff | فئة ADM — EA-ADM يُسقط ADM في قائمة Mini App | **ممنوعة** من قائمة السطح أصلًا |

**معالجة هذا العائق قرار تقني معماري** يُتخذ ضمن تفويض التنفيذ ومسار حوكمة المشروع (ADR يعدّل بوابة E-20 أو يصنف مسار الإدارة تصنيفًا صريحًا) — لا يُوصف كل تغيير برمجي بأنه «قرار مالك معلّق»، وما يحتاج المالك فعلًا هو الموارد والسياسات والحسابات لا الاختيار المعماري. **ولا يُحل العائق بتحويل قراءة الطاقم إلى P لتجاوز الحارس** (شرط «المنشور فقط» لا يناسب بيانات الإدارة) ولا بإضافة مسار جديد لمجرد تغيير تصنيفه وإخضار الحارس.

### 3.4 القنوات

طبقة المضيف الموجودة (`apps/customer-mini-app/src/host/`: telegram + browser). **مسار المتصفح ضمن الشريحة المستهدفة** (XR-8.3): OIDC النواة عبر `/edge/session/web` — نجاح تجربة تيليجرام وحدها لا يغلق ب.2 متعددة القنوات. تيليجرام ليس شرط التطبيق العام ولا هويته.

## 4. تجربة العقد — نُفّذت ونجحت (2026-10-24)

| الشرط | الدليل | النتيجة |
| --- | --- | --- |
| إصدار جلسة `customer` حقيقية | `app-edge-e2e` (منافذ الإنتاج ← تطبيق الهوية الحقيقي على منفذ حقيقي) | ✅ جلسة بمعرّف عامّ `WS-…` |
| الاستبدال بجمهور `marketplace` | نفس الاختبار — `ASSERTION_AUDIENCES_BY_ACTOR.customer` ∋ marketplace | ✅ تأكيد موقّع فعلاً |
| التأكيد يحمل الشخص/الفاعل/الجمهور/الممرّر | `verifyUserAssertion` (تحقق حقيقي) | ✅ sub=الشخص · act=customer · aud∋marketplace · via=customer-bot |
| المجهولة/المسحوبة تُرفضان | نفس الاختبار | ✅ `EdgeSessionRejectedError` |
| إنفاذ العضوية عند الحدّ | `marketplace` (Postgres حقيقي · نداء موقّع بـ`obo`) | ✅ المالك/النشط 200 · المختومة/غير العضو 404 · بلا obo رفض |
| فحص الرتبة للقراءة | تبع `listStaff` (المصدر: `app/stores.ts` — العضوية بلا رتبة للقراءة) | ✅ الرتبة للتعديل فقط |
| حدّ M1-05 | `authz-policy/policy.test.ts` (اختبار مسجّل) | ✅ `AUDIENCE_NOT_GRANTED` — منحة إنتاج تُتخذ بقرار تقني |

**ما لم يُثبت بعد (وذلك العائق المتبقي):** فتحُ مدخلِ القائمةِ إنتاجيًا (§3.3 — فئة N لا تُفتح إلا بدليل E-20 لا ينطبق دلاليًا على قرارات الإدارة).

## 5. معايير قبول الشريحة (بعد نجاح التجربة)

1. العضو المصرح (مالك أو موظف نشط — حسب ما يثبته تبع `listStaff`) يقرأ طاقم متجره — 200.
2. عضوية غير نشطة — `STORE_NOT_FOUND` (404 لا تسريب وجود).
3. متجر آخر — `STORE_NOT_FOUND`.
4. الجلسة المنتهية/المرفوضة — 401 مسمّى (`EDGE_UNAUTHENTICATED`).
5. إعادة الاستخدام بعد السحب تفشل.
6. التوقيعات متحققة فعليًا (`verifyServiceToken`): الاستبدال والنداء الخلفي — نمط اختبارات CLM-0696/0697.
